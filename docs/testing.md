# Testing & quality gate

Four automated layers, each with its own database (or none). Phase 10B turned them into the release gate: every layer must pass, and none of them touches the development database.

| Layer           | Command                    | Runs against                                                                                | What it proves                                                                                                                                         |
| --------------- | -------------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| API unit + HTTP | `npm run test -w @app/api` | mocked Prisma, real Nest pipeline                                                           | Services, guards, validation, error filter, env validation, CSRF/CORS/headers/proxy/rate limits (`test/security.e2e-spec.ts`), route-security metadata |
| Web             | `npm run test -w @app/web` | jsdom, mocked API                                                                           | Components, pages, routing, appearance engine, error boundaries                                                                                        |
| Database        | `npm run test:db`          | `app_test` (truncated before every test)                                                    | Real SQL: constraints, triggers, transactions, row locks, concurrency, tenant isolation, RBAC over HTTP, reports, time zones, integrity audit          |
| Browser E2E     | `npm run test:e2e`         | `app_e2e_test`, API build on :3100, web production build on :5174, installed Microsoft Edge | Critical user journeys in a real browser (below)                                                                                                       |

`npm run validate` runs format check, lint, typecheck, unit/web tests, the production build, and the build review (`npm run check:build`). Run `npm run test:db` and `npm run test:e2e` as well before finishing a phase.

## Browser E2E (`e2e/`)

[Playwright](https://playwright.dev) drives the **installed Microsoft Edge** (`channel: 'msedge'`, launched with `--lang=en-US` so `Intl` formats are deterministic). No browser is downloaded, and no Docker or WSL is involved.

- **Stack:** `playwright.config.ts` starts its own servers on their own ports (never the development servers): `e2e/support/prepare-db.ts` and then the compiled API (`apps/api/dist`) on `:3100`; `vite build` into `apps/web/dist-e2e` and `vite preview` on `:5174` (production build, real CSP headers). `npm run test:e2e` builds `shared` and the API first.
- **Database:** `app_e2e_test` (must end in `_test` and differ from `DB_NAME`). Every run creates it if missing, applies migrations, truncates every table, and seeds users, two workspaces, and memberships. The `seed` project then creates the catalog, stock, customers, and orders **through the real API**, and backdates five orders to fixed instants around midnight for the time-zone tests. Runs are repeatable and need no manual cleanup; the development database is never opened.
- **Sessions:** the E2E users get a session row and a Playwright storage state (`e2e/.auth/`, git-ignored), so tests don't sign in through the rate-limited form. The authentication tests sign in through the real form; the whole run stays below the login limit (10/minute).
- **After the run:** `support/global-teardown.ts` runs the read-only integrity audit on everything the tests did; a broken invariant fails the run.
- Tests run serially (one worker): they share one seeded database and the per-IP login limit.

## Database integrity audit

`npm run db:verify` (`apps/api/prisma/verify-integrity.ts`) runs 13 read-only checks in one read-only snapshot: movement arithmetic and chain, inventory = ledger, ledger rows have inventory, no negative stock, balanced transfers, order totals, SALE movements of fulfilled orders (one per line, matching product, warehouse, and quantity), none for unfulfilled orders, ORDER references, tenant relations, unique order numbers vs. the sequence, exactly one owner. It audits the database in `DB_NAME` (development by default), prints only check names and ids, and exits 1 on a violation. `integrity.db-spec.ts` proves it passes on API-written data, writes nothing, and detects each kind of broken invariant.

## Determinism rules

- Tests never depend on another test's leftovers: the DB suites truncate before every test; E2E recreates its database per run and every spec creates the records it mutates.
- HTTP tests that need a port use `listen(0)`; the E2E ports are fixed and `strictPort` (a busy port fails loudly instead of silently reusing another server).
- Fixed timestamps for time-sensitive data (`seed.setup.ts`); real-clock data is only compared within the same run.
- No random data without need: ids are generated by the system; names are fixed.
- The development database is only ever read by `npm run db:verify`, and written by `npm run db:seed` (idempotent) — never by a test.
